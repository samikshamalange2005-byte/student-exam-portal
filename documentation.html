1. Project Overview & Executive Summary

The College Examination Timetable & Room Management System is an end-to-end web portal designed to streamline university examination scheduling and eliminate physical notice-board bottlenecks.

The application provides two completely separated, role-based workflows:

  • Admin Portal (Exam Cell Faculty): Provides faculty administrators with tools to create exam schedules, define examination halls with seating capacities, enforce room capacity restrictions, and prevent overlapping room booking clashes.
  • Student Portal: Allows registered students to sign in and immediately access an uncluttered, personalized exam timetable that dynamically displays only the examinations applicable to their enrolled academic year and class section.
💡 30-Second Elevator Pitch for Viva / Interview:
"This project is a role-based full-stack web application that solves common examination logistics issues in colleges: it eliminates student confusion by strictly filtering exam timetables to a student's enrolled year and section, validates that assigned students do not exceed room seating limits, and mathematically prevents double-booking of exam venues at overlapping times."

2. Real-World Problems Solved

Traditional College Problem Consequences System Solution
Master Notice Board Clutter Students comb through huge 50-page PDFs or crowded notice boards, causing missed papers or confusion. Class-Specific Filtering: Students only see examinations for their specific Year and Section.
Room Double-Booking Clashes Two teachers schedule different exams in the same hall simultaneously, resulting in last-minute venue chaos. Mathematical Clash Prevention: System checks time intervals and rejects overlapping bookings for the same hall.
Hall Overcrowding Exams are assigned to small classrooms that cannot seat all enrolled students. Capacity Limit Validation: Server rejects exam scheduling if student count exceeds room capacity.

Component Breakdown:

  • Frontend (Vanilla HTML5, CSS3, ES6 JS): Lightweight, zero compilation build steps, fast loading, featuring custom CSS variables, responsive grids, and media print styling for student exam passes.
  • Backend (Node.js & Express.js): RESTful API server with asynchronous non-blocking I/O handling authentication, room management, and clash detection.
  • Database (MongoDB with Mongoose): High-performance NoSQL document store with strict Mongoose schema validation.
  • Authentication (JWT & BcryptJS): Passwords securely hashed with 10 salt rounds; stateless JWT tokens maintain session security without server-side memory overhead.

5. Core Algorithms & Logic Explained

A. Strict Class-Specific Timetable Filtering

When a student logs in and accesses GET /api/exams, the backend verifies their JWT token, extracting their enrolled year and section. The query strictly restricts the returned documents: 

if (req.user.role === 'student') {
  query.year = req.user.year;
  query.$or = [
    { section: req.user.section },
    { section: 'All' }
  ];
}

Guaranteed Result: A 2nd-year Section A student will never see 3rd-year Section B exams, preventing cross-class timetable confusion.

B. Room Seating Capacity Limit Check

Before an exam is created, the system checks the assigned student count against the room's maximum seating capacity: 

if (assignedStudents > targetRoom.capacity) {
  return res.status(400).json({
    message: `Room capacity exceeded! Room "${targetRoom.name}" has a capacity of ${targetRoom.capacity}, but ${assignedStudents} students are assigned.`
  });
}

C. Time-Interval Overlap Conflict Formula

To verify whether two exams scheduled in the same hall clash, start and end times are parsed into total minutes from midnight:

  • 10:00 AM = (10 × 60) + 0 = 600 minutes
  • 01:00 PM = (13 × 60) + 0 = 780 minutes

Given two time intervals [S1, E1] and [S2, E2], they overlap if and only if:

max(Start1, Start2) < min(End1, End2)

If this condition evaluates to true for any exam already booked in the same hall on that date, the request is rejected with HTTP 400 and a descriptive conflict alert. Consecutive sessions (e.g. 10:00 AM–01:00 PM and 02:00 PM–05:00 PM) do not overlap and are accepted cleanly.

8. Common Viva Questions & Model Answers

Q1: Why use JWT instead of standard cookie sessions?
JWT tokens are stateless and self-contained. The server does not maintain session memory, allowing the application to scale horizontally across multiple instances without sticky sessions or centralized Redis session stores.
Q2: How are passwords secured in the database?
Passwords are never stored in plaintext. They are encrypted using bcryptjs with 10 salt rounds, utilizing one-way salted hashing to resist rainbow table and dictionary attacks.
Q3: How does the clash detection algorithm work with 12-hour AM/PM times?
The backend parses 12-hour AM/PM strings into total minutes from midnight (0 to 1439). It then evaluates whether max(S1, S2) < min(E1, E2).
Q4: Can an admin delete a room that is currently in use?
No. The DELETE /api/rooms/:id route queries active scheduled exams assigned to that room and blocks deletion if active schedules exist, preserving relational data integrity.
